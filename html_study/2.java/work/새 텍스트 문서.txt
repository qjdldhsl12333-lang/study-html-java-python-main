

1. **@RestController** → 이 클래스는 JSON 쏘는 기계
2. **@RequestMapping / @GetMapping** → URL 들어오면 어떤 메서드 실행할지 정함
3. **@PathVariable /@RequestParam / @RequestBody** → 요청 값들을 꺼내오는 방법
4. **@ResponseEntity** → 상태코드 + JSON을 완전히 컨트롤해서 응답

SOLID원칙

1.단일 책임의 원칙(Single Responsibility Principle)(SRP)
하나의 클래스는 하나의 기능만 가져한다.
하나의 클래스에 기능 섞어두면 
수정할 때 너무 힘들다
테스트하기 힘들다
가독성이 떨어진다.

2. 개방 폐쇄의 원칙(Open Closed Principle)(OCP)
기능 확장에는 열려있고, 코드 수정에는 닫혀있다
새로운 요구사항이 생기면, 
기존 코드는 최대한 건드리지 않고, 
수정을 최소화 하는것이좋다.
상속, 구현을 통해서 확장하는 방향으로 해야함.

서비스 로직은 웬만하면 수정하지 않는 편이 좋다.

3.리스코프 치환 원칙 (Liskov Substitution Principle)(LSP)
부모 타입 객체를 사용하는곳에, 자식 타입객체를 넣어도 정상적으로 동작해야함.
(다형성)

4. 인터페이스 분리 원칙(Interface Segregation Principle)(ISP)
덩치큰 인터페이스 하나보다 ,작은 인터페이스 여러 개로 나누는게 낫다.

5.의존 역전 원칙 (Dependency Inversion Principle)(DIP)
구현체는 바뀌어도 인터페이스는 유지해라

개발을 할 때 범용성이 좋게 설계를 하는게 좋다.
확장을 염두해두고 개발을 하는게 좋다.
확장이 되도 핵심 로직은 크게 수정이 안되는 방향으로 하라

의존성 주입 방법

1. 필드주입
@Autowired를 붙여서 주입
필드에 final을 못써서 불변성을 보장하지 못한다.

2.생성자 주입
-스프링에서 가장 권장하는 방식
final을 쓸 수 있어서 의존성이 반드시 필요함을 명확히 표현할 수 있다.

@RequiredArgsConstructor를 이용해서 생성자 주입을 깔끔하게 할 수 있다.

3.setter주입

setter를 public으로 열어두면 외부에서 의도치 않게 다른 객체를 다시 넣어버릴수도 있다.
객체생명주기 중간에 의존성이 바뀔 수 있어서 코드 추적이 힘들어 질 수 있다.
